# Оценка результатов

Скрипт `eval/score.py` сравнивает эталон и результаты системы. Оба файла имеют формат `dev.jsonl`: одна строка - один кейс или полная история. Точные проверки выполняет Python, смысловые - LLM-судья через LangChain и OpenAI-совместимый API. Аудио и OCR пока не оцениваются

## Быстрый запуск

Команды выполняются из корня проекта в PowerShell. Нужен Python 3.10 или новее

```powershell
python -m pip install -r requirements.txt
```

Самопроверка на первых десяти кейсах без обращения к модели:

```powershell
python eval/score.py --gold eval/dev.jsonl --predictions eval/dev.jsonl --judge off --limit 10 --output report.json
```

Два одинаковых файла должны совпасть без вызовов LLM. Это проверка оценщика, а не результат работы агента

Для локальной модели на порту 1234:

```powershell
$env:OPENAI_BASE_URL = "http://localhost:1234/v1"
$env:JUDGE_MODEL = "gigachat3.1-10b-a1.8b"
python eval/score.py --gold eval/dev.jsonl --predictions predictions.jsonl --limit 10 --output report.json
```

Для внешнего провайдера задайте его `OPENAI_BASE_URL`, имя модели в `JUDGE_MODEL` и ключ в `OPENAI_API_KEY`. Параметры `--base-url` и `--model` имеют приоритет над переменными окружения. Локальному серверу ключ не нужен

Если зависимости установлены в локальное окружение проекта, замените `python` на `.venv/Scripts/python.exe`

> Путь `/api/v1/chat` из примера curl - собственный API сервера. LangChain использует OpenAI-совместимый `/v1/chat/completions`, поэтому `base-url` должен заканчиваться на `/v1`

## Какие файлы подавать

Первый файл содержит эталон. Во втором сохраняются `id`, `schema_version`, `dataset_version` и исходный `input`, а содержимое `gold` заменяется результатами системы. Название `gold` сохраняется ради одинакового формата

```text
gold.proposals                       Предложения до подтверждения
gold.expected_issues                 Обнаруженные вопросы и конфликты
gold.answers                         Ответы на запросы и сводки
gold.checks[].expected_state          Фактические снимки CRM
gold.checks[].expected_derived_views  Производные представления, если проверяются
```

Строки сопоставляются по ID кейса, а не по порядку. ID созданных задач могут отличаться от эталонных: оценщик сопоставляет задачи и учитывает соответствие при дальнейших обновлениях. Порядок операций не важен

В длинной истории результат привязывается к исходному шагу через `available_after`, `after` или `query_id`. Модель-исполнитель не должна видеть эталон. Оценщик не запускает агента и не подставляет операции gold вместо его результатов

## Как работает --limit

`--limit 10` выбирает первые 10 объектов эталонного файла в порядке строк. История со всеми эпизодами считается одним объектом и не разрезается. Без параметра оценивается весь файл. Лимит должен быть положительным целым числом

Во втором файле можно оставить все 100 результатов: известные кейсы за пределами выбранной десятки игнорируются. Неизвестные ID по-прежнему отражаются как ошибка покрытия. Если выбранный кейс отсутствует, он остается пропуском и снижает recall

В отчете `selection` содержит выбранные ID, размер исходного набора и число проигнорированных результатов. Оба JSONL читаются целиком: поврежденные строки и дубли ID не скрываются лимитом

## Что проверяет код

Факт диффа сравнивается по шагу, закупке, полю и значению. `set_field` считается одним фактом, `create_task` - одной составной задачей, `update_task` - отдельным фактом на каждое изменяемое поле. Неверное значение дает FP и FN, повтор правильного факта - дополнительный FP. Деньги сравниваются через `Decimal`; ноль, `null`, отсутствие поля и boolean различаются

Проверяются базовые ревизии, конфликтующие операции и сохранение пакетов. Цена, отделенная от обязательного условия оплаты в другой пакет, может получить балл за отдельное значение, но кейс целиком не пройдет

Состояния CRM сравниваются после всех заданных контрольных точек, включая задачи, ревизии и производные представления. Поля карточек образуют отдельные precision/recall досье. Они не смешиваются с оценкой диффа до действий закупщика

Числовые поля снимков и ответов сравниваются с эталоном. Отдельно проверяется арифметика: количество * цена и заказанное минус полученное. Если цена явно указана без НДС, добавляется заданная ставка; сумма округляется до копеек по `ROUND_HALF_UP`. Неизвестные ставки, доставку и скидки скрипт не выдумывает

Сводка сравнивается с эталонными списками просроченных задач, ближайших действий, поставок и задач без срока. Порядок элементов не важен, дубли сохраняются. Границы окна берутся из эталона для `input.now`: сегодня и следующие два календарных дня. Дата компьютера не используется

Pydantic-модели проверяют отдельно строки кейсов, операции, снимки CRM, сводки и ответы судьи. Включена строгая проверка типов: строки не превращаются в числа, а boolean не принимается за количество. Денежные значения могут быть числами или десятичными строками. Правильная структура не означает правильное содержание. Пропущенный документ снижает полноту, но не считается опубликованным невалидным документом

## Когда вызывается LLM

Судья нужен для разных формулировок одной задачи, названий поставщика, текстовых условий, объяснений и конфликтов. Числа, даты, технические ID и ревизии он не переоценивает вопреки точному сравнению

Существование цитаты проверяется кодом. Если факт и цитаты совпали с эталоном, используется имеющаяся разметка без запроса к модели. То же правило действует для расширенной цитаты из того же события, содержащей эталонный фрагмент. Однозначное несовпадение числового значения с эталонным фактом не переоценивается судьей. Для остальных альтернативных цитат судья проверяет, действительно ли они подтверждают факт с учетом условий, полномочий и последующих решений. Неверные текущие значения также проверяются на использование отмененных или опровергнутых сведений

Судья получает только доступные на оцениваемом шаге источники. Будущие реплики не оправдывают более раннее предложение. Встроенные команды из переписки и документов объявлены недоверенными данными

Ответ содержит `accepted`, `reason` и `source_ids`. Код проверяет JSON и ссылки на источники, затем сам считает метрики. Одинаковые запросы внутри запуска кэшируются

При ошибке формата повторный запрос содержит объяснение ошибки и список допустимых ID событий. Судья должен ссылаться на `event.id`, а не на идентификатор файла `source_id`. Невалидные ответы сохраняются в отчете для диагностики, сетевые ошибки записываются без содержимого исключения и секретов

`--timeout` задает таймаут запроса в секундах, по умолчанию 60. При ошибке выполняется `--retries` повторов, по умолчанию один. Затем проверка остается незавершенной - она не считается успешной. `--max-judge-chars` ограничивает контекст, по умолчанию 120 000 символов; слишком длинная история не обрезается молча

## Как читать отчет

В `report.json` находятся общие метрики, результаты по группам и каждому кейсу. `coverage` показывает пропуски, неизвестные ID и поврежденные строки. `judge_calls` сохраняет вердикты, источники, длительность и расход токенов. Также записываются конфигурация, версии пакетов и хэши входов

**Дифф и досье.** `diff_precision` / `diff_recall` проверяют предложения до действий пользователя, `dossier_precision` / `dossier_recall` - поля сохраненных карточек. Цели - 95% / 85%, критические пороги - ниже 90% / 75%

**Конфликты и память.** `conflict_recall` должен быть не ниже 90%, критический порог - ниже 80%. `answers_accuracy` показывает долю полностью правильных ответов без заданного порога. Старые и опровергнутые текущие значения, лишние вопросы и пропуски выводятся в отдельных счетчиках

**Источники.** `literal_citations` проверяет дословность, `supported_citations` - подтверждение факта. Цель обеих метрик - 100%

**Сводка.** `summary_precision` / `summary_recall` проверяют пункты, цель обеих - 95%, критический порог - ниже 90%. `summary_window_accuracy` проверяет границы окна, цель - 100%

**Запись, формат и расчеты.** `crm_checkpoints` / `crm_chains` проверяют снимки и целые цепочки. `case_schema_validity` проверяет формат кейса, `format_validity` - снимков и сводок. `calculation_accuracy` сравнивает числовые значения с gold, `arithmetic_consistency` проверяет формулы, `purchase_link_accuracy` - привязку предложений к закупкам. Цель - 100%; любая ошибка критична

Precision = TP/(TP+FP), recall = TP/(TP+FN). Общая оценка считается из суммы счетчиков, а не среднего процентов. Длинная история имеет больший вес; результаты по кейсам и группам позволяют это увидеть. В полях досье учитываются и явные `null`

Статус `ok` означает достижение цели, `below_target` - недостижение без пересечения критического порога, `critical` - пересечение порога. При нулевом знаменателе выводится `value: null`, `status: not_applicable`. При нерешенных проверках судьи - `incomplete` и консервативная нижняя граница. Эти статусы не означают 100%

## Ограничения и тесты

Снимки CRM не доказывают реальную атомарность транзакции и отсутствие повторного физического применения события. Для этого нужен журнал исполнения раннера. Такие проверки, аудио/OCR и произвольные текстовые запреты перечислены в `not_evaluated`. `all_structured_cases_match` относится только к реализованным проверкам представленных данных

```powershell
python -m unittest discover -s eval/tests -v
```

Интеграционный тест использует локальный HTTP-сервер и настоящий LangChain без внешнего API. Ему нужен доступ к loopback

Код возврата 0 означает, что отчет построен, а не что все цели достигнуты. Код 2 означает ошибку входа или конфигурации. Выходной файл не может перезаписать входные JSONL

## Пробный прогон локальной модели

В [examples/local-smoke.predictions.jsonl](examples/local-smoke.predictions.jsonl) находятся десять синтетических результатов E01-E10. Они получены из gold, а не от агента: расширены девять цитат, переформулированы три задачи и намеренно испорчена цена E10 (`11999.00` вместо `12000.00`). Снимки CRM оставлены эталонными, поэтому их совпадение не проверяет реальное исполнение

Пробный запуск выполнялся через `gigachat3.1-10b-a1.8b` на `http://localhost:1234/v1`: обработаны 10 кейсов, выполнены три смысловые проверки LLM. Все три переформулировки приняты, неверная цена обнаружена кодом: TP=18, FP=1, FN=1; precision и recall диффа - 94,74%. Незаполненных вердиктов и ошибок API не было. Сводок в этой десятке нет, соответствующие метрики имеют статус `not_applicable`. Отчет прогона в репозитории не хранится; его можно получить повторным запуском

Для повторения после настройки переменных окружения из начала инструкции:

```powershell
python eval/score.py --gold eval/dev.jsonl --predictions eval/examples/local-smoke.predictions.jsonl --limit 10 --output smoke-report.json
```
